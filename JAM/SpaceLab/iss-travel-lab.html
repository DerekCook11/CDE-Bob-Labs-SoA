Key Concepts

The "why" behind what Bob does in each prompt.

Why system-scope Maven dependencies cause build failures▼
A <scope>system</scope> dependency tells Maven to read a JAR from a hard-coded filesystem path. This bypasses Maven's repository system entirely and ties the build to a specific machine. Maven 3.9 requires the path to be an absolute literal — environment variable expansions like ${env.WAS_HOME} are rejected before compilation even starts. The correct approach is <scope>provided</scope> with a standard Maven coordinate that resolves from a repository.
javax.servlet vs jakarta.servlet — why no imports need renaming▼
When the Jakarta EE project took stewardship of Java EE, it eventually renamed all packages from javax.* to jakarta.*. That rename happened at Jakarta EE 9 (Servlet 5.0). The target of this migration is Jakarta EE 8 (Servlet 4.0), which still uses javax.servlet.*. The artifact jakarta.servlet:jakarta.servlet-api:4.0.4 has the new groupId on Maven Central but the classes inside remain in javax.servlet. Zero import changes are needed in the existing Java files.
Why the EAR module can be removed▼
WebSphere required all applications to be packaged as Enterprise Application Archives (EARs). Open Liberty supports direct WAR deployment — you list the WAR in server.xml and set a context root. The EAR in this project contained only one useful piece of data: the context root /iss-travel. That moves to server.xml. Removing the EAR reduces the Maven reactor from two modules to one and eliminates ~30 lines of configuration with zero functional loss.
What maven.compiler.release does that source/target doesn't▼
The old source/target pair controls syntax compatibility and bytecode version — but it does not prevent you from accidentally calling APIs that only exist in newer JDKs. The --release N flag (exposed as maven.compiler.release) also locks the bootstrap classpath, so the compiler refuses any API not available in Java N. It is a single, stronger guarantee that replaces two properties.
Why IBM deployment descriptors can be deleted without replacement▼
Files like ibm-web-bnd.xml use the proprietary XML namespace http://websphere.ibm.com/xml/ns/javaee. The Servlet specification says containers must ignore unrecognised files in WEB-INF/, so on Tomcat, Jetty, or Liberty these files are silently parsed and discarded. They only have effect on WebSphere. Liberty does not need a replacement because the security role binding they provided is either handled in server.xml or simply not required when no authentication is configured.
Why IBM Bob prompts are better than manual edits for migration tasks▼
Manual migration involves reading every file, mentally tracking dependencies between changes, and running the build after each edit. Bob reads the entire codebase before making any changes, understands inter-file dependencies (e.g. knowing that deleting WebSphereSecurityUtil.java requires also changing TravelServlet.java), applies all changes atomically, and immediately validates by running the build. If the build fails Bob iterates automatically. The result is a complete, verified migration in a single prompt rather than dozens of careful manual steps.

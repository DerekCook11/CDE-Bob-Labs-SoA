Step 1

Analyze & Plan

Open the extracted modresorts-twas-j8 project in Bob.

Prompt to Bob

Analyze this legacy Java application and create a modernization plan.

Identify:
- Current architecture and Java version
- Major application components
- Maven dependencies
- Traditional WebSphere-specific APIs and dependencies
- Deprecated APIs
- Technical debt and compatibility risks
- Runtime libraries used by the code but not explicitly packaged in the WAR
- Static frontend assets referenced by HTML/JSP but missing from the source tree

Modernization requirements:
- Keep the application as a monolith
- Migrate Java 8 to Java 17
- Replace traditional WebSphere-specific APIs with standard Java, Servlet, or JNDI alternatives where possible
- Remove obsolete WebSphere dependencies such as was_public when no longer required
- Keep the existing JSP/HTML frontend
- Preserve existing business functionality
- Continue packaging as a WAR
- Run locally on Open Liberty

Do not introduce:
- Microservices
- Kubernetes or OpenShift
- React
- Database migration
- CI/CD

Provide a concise modernization plan before making changes.

Pay special attention to:
- Gson or other runtime libraries that may compile but be missing at runtime
- Missing JavaScript Library in legacy codebase leading to Pikaday not being defined
- Restricted date ranges configured in legacy codebase calendar
- Static resources such as JavaScript/CSS files referenced by the UI but absent from the repository
- Maven Surefire/JaCoCo configuration that must work both with mvn clean verify and mvn liberty:dev
Expected findings: Bob should identify WebSphere-specific usage such as WSSecurityHelper, ResponseUtils, ServerName, WsnInitialContextFactory, and the was_public Maven dependency.
Step 2

Modernize & Build

Prompt to Bob

Implement the approved modernization plan.

Perform the required code and configuration changes.

Then run:

mvn clean package

Continue fixing compilation, dependency, or configuration issues until:

- Java target is 17
- Traditional WebSphere-specific APIs have been removed or replaced as planned
- was_public is removed if no longer required
- Required runtime libraries are explicitly packaged in the WAR
- Referenced frontend assets are present and packaged
- WAR is generated
- BUILD SUCCESS

At completion, briefly report:
- Files changed
- Key APIs/dependencies removed or replaced
- Any missing runtime dependencies/assets found and fixed
- WAR location
- Remaining warnings
Checkpoint 2 — Modernization Complete
Confirm Java 17, the intended WebSphere API replacements, removal of was_public if no longer needed, and a successful WAR build.
Typical changes Bob may make
  • LogoutServlet: WSSecurityHelper → standard servlet logout/session invalidation.
  • UpperServlet: ResponseUtils → portable HTML escaping.
  • WeatherServlet: ServerName → standard Java runtime properties.
  • WeatherServlet: WsnInitialContextFactory → standard InitialContext.
  • pom.xml: Java 8 → Java 17 and removal of was_public where no longer needed.
Common issue: Missing runtime dependency (for example Gson)

If Liberty starts but a servlet fails with NoClassDefFoundError: com/google/gson/Gson, check whether Gson is declared and packaged:

mvn dependency:tree | grep -i gson
jar tf target/modresorts-2.0.0.war | grep -i gson

If Gson is required, ensure it is a normal application dependency (not provided) so it is packaged under WEB-INF/lib.

Common issue: Referenced frontend asset is missing

If the browser reports Pikaday is not defined or Liberty logs File not found: /lib/pikaday.js, verify the asset:

grep -Rni "pikaday.js" .
find . -iname '*pikaday*'
jar tf target/modresorts-2.0.0.war | grep -i pikaday

If index.html references lib/pikaday.js, the corresponding asset must be packaged, typically from WebContent/lib/pikaday.js. Treat this as a pre-existing frontend defect discovered during modernization, not as a Liberty defect.

Step 3

Test & Quality

Prompt to Bob

Create and run an automated test harness for WeatherServlet.

Use:
- JUnit 5
- Mockito
- Spring Test mock servlet objects
- JaCoCo
- Maven Surefire configured so tests work with both mvn clean verify and mvn liberty:dev

Do not use live external weather services.

Configure JaCoCo/Surefire so no unresolved literal @{argLine} is passed to the test JVM. Use a dedicated JaCoCo property (for example jacocoArgLine) with a safe empty default if needed.

Test meaningful normal, edge, and error scenarios.

Run:

mvn clean verify

Continue fixing issues and adding meaningful tests until:

- All tests pass
- Failures = 0
- Errors = 0
- WeatherServlet line coverage >= 80%
- WAR is generated
- BUILD SUCCESS

Do not disable tests or lower the coverage threshold.

Report only:
- Test count
- Failures/errors
- Coverage percentage
- Final build status
Checkpoint 3 — Build & Quality
Success requires all tests passing, zero failures/errors, WeatherServlet line coverage ≥80%, WAR generated, and BUILD SUCCESS.

JaCoCo report:

target/site/jacoco/index.html
Common issue: Error: could not open {argLine} in Liberty dev mode

This means Surefire is passing an unresolved @{argLine} to Java. Use a dedicated JaCoCo property with an empty default:

<properties>
  <jacocoArgLine></jacocoArgLine>
</properties>

<configuration>
  <propertyName>jacocoArgLine</propertyName>
</configuration>

<configuration>
  <argLine>@{jacocoArgLine}</argLine>
</configuration>

Then rerun mvn clean verify before starting mvn liberty:dev.

Step 4

Run, Verify & Document

Prompt to Bob

Run the modernized application locally on Open Liberty.

Use the existing Liberty server.xml where appropriate.

Start Liberty with:

mvn liberty:dev

Verify:

curl -I http://localhost:9080/resorts/

Also verify important static/runtime dependencies when applicable, for example:

curl -I http://localhost:9080/resorts/lib/pikaday.js

and review the Liberty console for runtime classloading errors.

Success criteria:
- Liberty starts successfully
- ModResorts deploys successfully
- /resorts returns HTTP 200
- The application page loads successfully
- Browser console has no missing-resource errors for required app assets
- Liberty log has no NoClassDefFoundError / ClassNotFoundException for required app libraries
- Key runtime flow such as date/availability selection works

After verification, create one final interactive HTML modernization report named:

modresorts-modernization-final-report.html

Include:
- Original architecture
- Modernized architecture
- Java 8 → Java 17
- WebSphere APIs/dependencies removed or replaced
- Files changed
- Maven changes
- Build result
- Test result
- Coverage result
- Liberty deployment result
- HTTP verification
- Remaining warnings or risks
- Before vs. after architecture diagram
- Runtime issues discovered during validation and how they were resolved
  - missing frontend assets such as pikaday.js, if encountered
  - missing runtime libraries such as Gson, if encountered
  - Maven Surefire/JaCoCo argLine issue, if encountered
  - stale Liberty workarea/redeploy issue, if encountered

Also include a clear Before vs. After Change Matrix covering:
- Java version
- Runtime
- WebSphere-specific APIs
- Maven dependencies
- JNDI usage
- WAR packaging
- Frontend
- Application architecture

For each important modernization change, show a concise before/after code example where applicable, including:
- WSSecurityHelper → standard Servlet logout/session handling
- ResponseUtils → portable HTML escaping
- ServerName → standard Java runtime properties
- WsnInitialContextFactory → standard InitialContext

Add a section titled "What Did Not Change" and explicitly state:
- The application remains a monolith
- Existing business functionality is preserved
- JSP/HTML frontend remains
- WAR packaging remains
- No database migration was performed
- No microservices were introduced
- No Kubernetes or OpenShift was introduced
- No React migration was performed
- No CI/CD implementation was performed

Keep the report concise, evidence-based, and focused on what actually changed versus what stayed the same.
Checkpoint 4 — Runtime Verification
Success requires Liberty startup, successful ModResorts deployment, and HTTP 200 from /resorts.

Common issue: Liberty workarea becomes stale after repeated hot reloads

If Liberty reports CWWKE0701E with a missing workarea/.../bundleFile, stop dev mode and rebuild from a clean target:

# Stop liberty:dev with Ctrl+C
rm -rf target
mvn clean package
mvn liberty:dev

Workshop Overview

App Modernization: Same App, Modern Foundation

What This Workshop Is About

In this workshop, you will use IBM Bob to modernize a small legacy Java web application called ModResorts.

ModResorts is a traditional Java web application that represents a resort reservation experience. It uses Java servlets, JSP/HTML, configuration files, and older IBM WebSphere-specific APIs and dependencies.

The application itself is not being redesigned. The goal is to keep the same application and the same business behavior, but move it onto a more modern and portable foundation.

During the lab, IBM Bob will help you analyze the application, create a modernization plan, migrate from Java 8 to Java 17, replace WebSphere-specific APIs with portable alternatives, update the Maven build, create automated tests, run the application on Open Liberty, verify that it still works, and generate a final before-and-after modernization report.

This is not a rewrite. You are not converting the application to microservices, React, Kubernetes/OpenShift, a new database, or a CI/CD architecture.

Workshop goal: Take an existing application, remove older platform dependencies, update the Java runtime, move it to Open Liberty, and prove that it still works.

At the end of the workshop, you should have the same ModResorts application running on Java 17 and Open Liberty, together with passing tests and a final report showing exactly what changed and what stayed the same.

Step 1

Analyze & Plan BOB PLAN MODE

Open the extracted modresorts-twas-j8 project in Bob.

Prompt to Bob

Analyze this legacy Java application and create a modernization plan.

Identify:
- Current architecture and Java version
- Major application components
- Maven dependencies
- Traditional WebSphere-specific APIs and dependencies
- Deprecated APIs
- Technical debt and compatibility risks
- Runtime libraries used by the code but not explicitly packaged in the WAR
- Static frontend assets referenced by HTML/JSP but missing from the source tree

Modernization requirements:
- Keep the application as a monolith
- Migrate Java 8 to Java 17
- Replace traditional WebSphere-specific APIs with standard Java, Servlet, or JNDI alternatives where possible
- Remove obsolete WebSphere dependencies such as was_public when no longer required
- Keep the existing JSP/HTML frontend
- Preserve existing business functionality
- Continue packaging as a WAR
- Run locally on Open Liberty

Do not introduce:
- Microservices
- Kubernetes or OpenShift
- React
- Database migration
- CI/CD

Provide a concise modernization plan before making changes.

Save the approved plan in the project as:

modernization-plan.md

Do not make application code changes in this step.

Pay special attention to:
- Gson or other runtime libraries that may compile but be missing at runtime
- Missing JavaScript Library in legacy codebase leading to Pikaday not being defined
- Restricted date ranges configured in legacy codebase calendar
- Static resources such as JavaScript/CSS files referenced by the UI but absent from the repository
- Maven Surefire/JaCoCo configuration that must work both with mvn clean verify and mvn liberty:dev

Scope guardrail:

Do not migrate javax.* packages to jakarta.*.

Keep the existing Java EE / javax.servlet namespace unless a specific
WebSphere proprietary API must be replaced.

This lab is not a Jakarta EE namespace migration.

The modernization target is:
- Java 8 → Java 17
- Traditional WebSphere dependencies/APIs → portable Java/Servlet/JNDI alternatives
- Open Liberty runtime
- Existing monolithic WAR application
- Existing JSP/HTML frontend
- Existing business behavior

Do not expand scope beyond this.
Expected findings: Bob should identify WebSphere-specific usage such as WSSecurityHelper, ResponseUtils, ServerName, WsnInitialContextFactory, and the was_public Maven dependency.

Typical changes Bob may make
  • LogoutServlet: WSSecurityHelper → standard servlet logout/session invalidation.
  • UpperServlet: ResponseUtils → portable HTML escaping.
  • WeatherServlet: ServerName → standard Java runtime properties.
  • WeatherServlet: WsnInitialContextFactory → standard InitialContext.
  • pom.xml: Java 8 → Java 17 and removal of was_public where no longer needed.
Common issue: Missing runtime dependency (for example Gson)

If Liberty starts but a servlet fails with NoClassDefFoundError: com/google/gson/Gson, check whether Gson is declared and packaged:

mvn dependency:tree | grep -i gson
jar tf target/modresorts-2.0.0.war | grep -i gson

If Gson is required, ensure it is a normal application dependency (not provided) so it is packaged under WEB-INF/lib.

Common issue: Referenced frontend asset is missing

If the browser reports Pikaday is not defined or Liberty logs File not found: /lib/pikaday.js, verify the asset:

grep -Rni "pikaday.js" .
find . -iname '*pikaday*'
jar tf target/modresorts-2.0.0.war | grep -i pikaday

If index.html references lib/pikaday.js, the corresponding asset must be packaged, typically from WebContent/lib/pikaday.js. Treat this as a pre-existing frontend defect discovered during modernization, not as a Liberty defect.

Step 3

Test & Quality BOB AGENT MODE

Prompt to Bob

Create and run an automated test harness for WeatherServlet.

Use:
- JUnit 5
- Mockito
- Spring Test mock servlet objects
- JaCoCo
- Maven Surefire configured so tests work with both mvn clean verify and mvn liberty:dev

Do not use live external weather services.

Configure JaCoCo/Surefire so no unresolved literal @{argLine} is passed to the test JVM. Use a dedicated JaCoCo property, such as jacocoArgLine, with a safe empty default if needed.

Configure JaCoCo with a coverage CHECK rule specifically for:

com.acme.modres.WeatherServlet

Require:

LINE coverage >= 80%

The Maven build must FAIL automatically if WeatherServlet line coverage is below 80%.

Test meaningful normal, edge, and error scenarios, including where applicable:
- supported city paths
- null or missing city
- invalid city
- fallback/default weather behavior
- missing API key
- API key present
- successful mocked upstream response
- non-2xx upstream response
- connection or IO failure
- doPost delegation
- servlet initialization/destruction paths

Run:

mvn clean verify

After each run:
1. Confirm all tests pass.
2. Confirm failures = 0.
3. Confirm errors = 0.
4. Read the actual WeatherServlet line coverage from target/site/jacoco/jacoco.xml.
5. If coverage is below 80%, identify uncovered executable lines/branches, add meaningful tests, and rerun mvn clean verify.

Continue until ALL are true:
- All tests pass
- Failures = 0
- Errors = 0
- WeatherServlet line coverage >= 80%
- JaCoCo coverage check passes
- WAR is generated
- BUILD SUCCESS

Do not:
- disable or skip tests
- lower the coverage threshold
- exclude WeatherServlet from coverage
- add meaningless tests only to inflate coverage
- change business behavior solely to improve coverage

Do not stop simply because mvn clean verify returns BUILD SUCCESS.

At completion, report only:
- Total tests
- Failures
- Errors
- WeatherServlet line coverage
- JaCoCo coverage check result
- WAR path
- Final build status
Checkpoint 3 — Build & Quality
Success requires all tests passing, zero failures/errors, WeatherServlet line coverage ≥80%, WAR generated, and BUILD SUCCESS.

JaCoCo report:

target/site/jacoco/index.html
Common issue: Error: could not open {argLine} in Liberty dev mode

This means Surefire is passing an unresolved @{argLine} to Java. Use a dedicated JaCoCo property with an empty default:

<properties>
  <jacocoArgLine></jacocoArgLine>
</properties>

<configuration>
  <propertyName>jacocoArgLine</propertyName>
</configuration>

<configuration>
  <argLine>@{jacocoArgLine}</argLine>
</configuration>

Then rerun mvn clean verify before starting mvn liberty:dev.

import xml.etree.ElementTree as ET
root = ET.parse("target/site/jacoco/jacoco.xml").getroot()
found = False
for pkg in root.findall("package"):
    if pkg.get("name") == "com/acme/modres":
        for cls in pkg.findall("class"):
            if cls.get("name") == "com/acme/modres/WeatherServlet":
                for c in cls.findall("counter"):
                    if c.get("type") == "LINE":
                        missed = int(c.get("missed"))
                        covered = int(c.get("covered"))
                        total = missed + covered
                        pct = (covered / total * 100) if total else 0
                        print(f"WeatherServlet line coverage: {pct:.1f}%")
                        print("PASS" if pct >= 80 else "FAIL")
                        found = True
if not found:
    print("FAIL: WeatherServlet coverage counter not found")

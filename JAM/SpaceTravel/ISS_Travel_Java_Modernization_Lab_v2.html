ISS Travel App — Java Modernization Lab

Use IBM Bob to analyze and modernize a legacy Java 8 / Java EE 7 / WebSphere application into a Java 17 / Open Liberty application while preserving the UI and REST behavior.
Legacy Java 8 Java EE 7 WebSphere 9 EAR + WAR Target: Java 17 Target: Open Liberty

Lab Goal

Modernize the provided ISS Travel App using IBM Bob. The application intentionally contains WebSphere-specific APIs and deployment artifacts so Bob has a realistic modernization task.

Starting RuntimeJava 8
Starting ServerWebSphere 9
Target RuntimeJava 17
Target ServerOpen Liberty

Workshop Flow

STEP 0 — RUN BEFORE Legacy UI / Java 8 / WebSphere coupling | v STEP 1 — ANALYZE modernization-assessment.md | v STEP 2 — PLAN modernization-plan.md | v STEP 3 — MODERNIZE Bob changes code, build, runtime | v STEP 4 — RUN AFTER Java 17 + Open Liberty | v COMPARE Same business behavior, modern platform
Workshop message: the business application and user experience are preserved while the underlying Java and application-server platform are modernized.

Before vs After

Before

Browser | v index.html + main.js | v WebSphere Application Server 9 | +-- ISS Travel WAR +-- WebSphere APIs +-- IBM descriptors +-- was-public-api | v EAR + WAR Java EE 7 Java 8

Target

Browser | v index.html + main.js | v Open Liberty | +-- ISS Travel WAR +-- Standard Servlet APIs +-- server.xml | v WAR only Java EE 8 / Servlet 4 Java 17

Step 0 — Run the Legacy Application / Capture the Before State

The workshop should begin by showing participants the application before modernization. This creates a visible baseline for the final comparison.

A. Preview the legacy portal UI

From the legacy web application directory:

cd ~/Downloads/ISS/iss-travel-legacy/legacy-web/src/main/webapp
python3 -m http.server 8080

From another terminal, confirm that the page is being served:

curl -I http://localhost:8080
curl -s http://localhost:8080 | grep "ISS Travel App"
Expected: HTTP 200 and the portal should display the ISS Travel App UI with the legacy badges: Legacy Java EE 7, IBM WebSphere 9, and Java 8.

B. What should participants see?

  • Existing travel requests.
  • The Add Travel Request form.
  • Traveler, destination, purpose, departure date, and status fields.
  • The browser UI itself loads successfully.
Important: when the application is served only through Python's static web server, the UI is visible but the Java API is not running. Therefore GET /api/trips and POST /api/trips will not work yet. This is expected.

C. Demonstrate the legacy backend dependency

Return to the project root and attempt the actual Maven build:

cd ~/Downloads/ISS/iss-travel-legacy
echo $WAS_HOME
mvn clean package
Expected legacy failure: the build should fail because the project expects the WebSphere runtime JAR through ${env.WAS_HOME}/plugins/com.ibm.ws.runtime.jar.

Step 1 — Ask Bob to Analyze Only

In Bob Agent Mode, open the complete iss-travel-legacy project and use the following prompt.

Analyze this legacy Java application and do not modify any files yet.

The application is an ISS Travel App originally designed for:

- Java 8
- Java EE 7
- IBM WebSphere Application Server 9
- EAR + WAR packaging

The current development environment has:

- Java 17
- Maven 3.9
- No IBM WebSphere installation

The current build fails with:

'dependencies.dependency.systemPath' for
com.ibm.websphere:was-public-api:jar
must specify an absolute path but is
${env.WAS_HOME}/plugins/com.ibm.ws.runtime.jar

Please analyze the complete project and produce a modernization assessment.

Identify:

1. Java 8 dependencies and compiler settings.
2. WebSphere-specific Java APIs.
3. IBM-specific deployment descriptors.
4. EAR/WAR packaging dependencies.
5. Maven dependencies tied to WebSphere.
6. Java EE / javax dependencies.
7. What prevents this application from running on a vanilla Java environment.
8. What should be changed to migrate the application to Java 17 and Open Liberty.
9. Which existing application behavior and REST APIs must be preserved, including the ability to add a new travel request and immediately display it in the portal.

Do not change any files yet.

Create a file called:

modernization-assessment.md

Include:
- current architecture
- identified technical debt
- WebSphere dependencies
- Java version dependencies
- migration risks
- recommended target architecture
- proposed modernization steps
Checkpoint: Confirm Bob created modernization-assessment.md and did not modify application source files.

Step 2 — Ask Bob to Create the Modernization Plan

Now create a detailed modernization plan based on modernization-assessment.md.

Target architecture:

- Java 17
- Open Liberty
- standard Servlet APIs
- WAR-only deployment
- no WebSphere runtime dependency
- no com.ibm.websphere.* imports
- no com.ibm.ws.* imports
- no IBM-specific deployment descriptors
- preserve index.html and main.js
- preserve GET /api/trips
- preserve POST /api/trips
- preserve GET /api/trips?id=<id>
- preserve GET /api/health
- preserve the existing JSON response structures
- preserve the Add Travel Request form and immediate table refresh

Do not perform the migration yet.

Create:

modernization-plan.md

Show every file that will need to be changed, removed, or created.
Checkpoint: Review modernization-plan.md before allowing Bob to modify the code.

Step 3 — Ask Bob to Perform the Modernization

This is the execution step. Bob should now modify, build, run, verify, and document the application.

Implement the modernization plan now.

Use modernization-assessment.md and modernization-plan.md as the source of truth.

Modernize the ISS Travel App to the following target state:

- Java 17
- Open Liberty
- WAR-only deployment
- Standard Servlet APIs
- No WebSphere runtime dependency
- No com.ibm.websphere.* imports
- No com.ibm.ws.* imports
- No was_public.jar or com.ibm.ws.runtime.jar dependency
- Remove the legacy EAR module if it is no longer required
- Remove IBM-specific deployment descriptors:
  - ibm-web-bnd.xml
  - ibm-web-ext.xml
  - ibm-metadata.xml
- Add an Open Liberty server.xml
- Add the Liberty Maven plugin
- Preserve index.html and main.js
- Preserve these endpoints:
  - GET /api/trips
  - POST /api/trips
  - GET /api/trips?id=<id>
  - GET /api/health
- Preserve the existing JSON response structure and sample travel data
- Preserve the Add Travel Request form and its ability to immediately show the new request in the table

After making the changes:

1. Run mvn clean package.
2. Fix any compilation or dependency errors.
3. Run the application on Open Liberty.
4. Verify /api/health returns HTTP 200.
5. Verify GET /api/trips returns the expected travel records.
6. Verify POST /api/trips creates a new travel request and returns HTTP 201.
7. Verify the newly created request appears when GET /api/trips is called again.
8. Verify /api/trips?id=1001 returns the expected record.
9. Search the project to confirm there are no remaining:
   - com.ibm.websphere.*
   - com.ibm.ws.*
   - WAS_HOME references
   - com.ibm.ws.runtime.jar references
10. Confirm the IBM-specific deployment descriptors have been removed.
11. Confirm the application is compiling with Java 17.

Do not change the business behavior or browser UI unless required for compatibility.

Create a final report named:

iss-travel-modernization-final-report.html

The report should include:

- Executive summary
- Before architecture
- After architecture
- Files changed
- Files removed
- Files created
- Java 8 to Java 17 changes
- WebSphere to Open Liberty changes
- Dependencies removed
- Dependencies added
- Before and after Maven build results
- API verification results
- Remaining risks or follow-up items
Expected result: The same application behavior should now run on Java 17 + Open Liberty without WebSphere-specific dependencies.

Step 4 — Run the Modernized Application / Capture the After State

After Bob completes the modernization, participants should run the new application and prove that the same business behavior works on Java 17 + Open Liberty.

A. Build the modernized application

mvn clean package
Expected: BUILD SUCCESS.

B. Start Open Liberty

Use the Liberty Maven goal or command generated by Bob. A typical example is:

mvn liberty:run
If Bob generates a different module-specific command, use that command instead.

C. Verify the modernized UI

Open the modernized application URL in the browser. Depending on the context root, this is commonly:

http://<VM-IP>:9080/iss-travel/

Confirm that the portal still shows:

  • ISS Travel App
  • Existing travel requests
  • Add Travel Request form
  • Traveler, destination, purpose, departure date, and status

D. Add a new travel request from the browser

Enter a sample request such as:

FieldExample
TravelerSarah Mitchell
DestinationHouston, TX
PurposeMission operations workshop
Departure Date2026-12-05
StatusPENDING
Expected: the request is created, assigned a new ID, and immediately appears in the travel-request table.

E. Verify the same operation through the API

curl -i -X POST http://localhost:9080/iss-travel/api/trips \
  -H "Content-Type: application/json" \
  -d '{
    "traveler":"Sarah Mitchell",
    "destination":"Houston, TX",
    "purpose":"Mission operations workshop",
    "departureDate":"2026-12-05",
    "status":"PENDING"
  }'
Expected: HTTP 201 Created and JSON containing the new request ID.

F. Confirm the new request appears

curl -s http://localhost:9080/iss-travel/api/trips

What the Student Learned

  • How to identify Java version and application-server coupling.
  • How WebSphere-specific APIs reduce application portability.
  • How Bob separates assessment, planning, execution, and verification.
  • How to migrate a Java 8 / Java EE 7 application to Java 17 / Open Liberty.
  • How to validate modernization without changing business behavior.
  • How to prove the same UI and create/read travel-request functions work before and after modernization.
